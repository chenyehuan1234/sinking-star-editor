# v0.9 性能记录

## 2026-11-18 · alpha.9 工作台诊断

在「操作设置 → 性能诊断」点击「开始记录」，复现问题，再用底栏停止并查看报告。单次最多 30 秒。报告可手动导出 JSON，记录操作阶段、相对时间、场景类型及规模，不含路径、工程名称、关卡名称和对象 ID。

以下为本机离屏 Electron 1366×768 实际鼠标输入结果。测试使用独立工作区，只读原版数据。小关为多高度原版关卡 `green_metamirror`，大地图分区包含约 8,600–16,200 条记录、29,000–71,000 格地形。采样期间未启动游戏。

| 操作／阶段 | 样本 | P95 |
|---|---:|---:|
| 多高度小关，预热后从鼠标按下到高亮绘制 | 23 | 46.0 ms |
| 同一小关，物件拖动帧间隔 | 48 | 18.1 ms |
| 地形框选和物件放置交替，地形拖动帧间隔 | 16 | 50.5 ms |
| 同一轮放置，虚像更新 CPU | 13 | 3.7 ms |
| 密集大地图，分区预览请求往返 | 4 | 1,341 ms |
| 密集大地图，预览后台处理（含差量） | 4 | 444 ms |

小关选择和物件拖动达到 100 ms／33 ms 的目标。地形拖动未达标。三次物件拖动在松手前均无后台预览请求，松手后各产生一次。关闭／打开记录的同批小关外部输入对照中，选择 P95 为 65.9／66.3 ms，拖动为 17.9／17.9 ms。外部输入测法包含额外的帧等待。

密集世界的分区差量已改由后台生成，避免把完整前后分区交给界面线程比较。在同一场景复测中，预览往返仍约 1.34 秒，完整采样还记录到最长约 1.43 秒的界面长任务。最初基线因缓存命中事件占满采样上限只适合定位，不用于计算提速比例。最终报告共 2,368 个样本，无丢弃。

同轮世界采样中，最慢的预览合并为 25 ms，物件同步为 128 ms、地形同步为 112 ms、渲染调用为 363 ms。地形放置轮的单次拖动事件处理 P95 为 0.3 ms，渲染调用 P95 为 26.3 ms。当前测量表明卡顿还涉及场景应用、渲染及调度，尚未将最长停顿完整归因。

另一轮独立派生缓存复核中，小关选择、物件拖动、地形拖动及世界预览往返 P95 分别为 42.9 ms、18.0 ms、51.7 ms、1,371 ms。两轮都复现了密集区域加载时的大停顿。

大地图首次拉取源模型和贴图的端到端 P95 约为 1.11 秒和 1.05 秒，包含资源队列、读取、解码、传输和界面调度；源贴图读取阶段 P95 约为 696 ms，也包含并发读取等待。报告分列内存复用、磁盘缓存、源读取、解码及传输边界。传输边界以两端耗时差估算，包含调度。帧间隔与渲染 CPU 是应用端观测，未同步测量 GPU 或实际显示。

同机简化场景复跑见下表，脚本直接测画布操作路径，用于对照规模影响。

| 场景 | 选择 P95 | 拖动反馈 P95 | JS 堆阶段净增 |
|---|---:|---:|---:|
| 100 个简化物件 | 12.9 ms | 17.8 ms | 8.7 MiB |
| 1,000 个简化物件 | 14.3 ms | 18.5 ms | 20.2 MiB |
| 5,000 个简化物件 | 36.2 ms | 23.9 ms | 83.0 MiB |

堆变化来自离屏 Chromium 的 `usedJSHeapSize`，会受垃圾回收影响，未计 GPU、后台线程及其他进程内存。

复现时先运行 `npm run build`，设置 `SINKING_STAR_GAME`，再依次运行 `node scripts/benchmark.mjs` 和 `node scripts/diagnostics-benchmark.mjs`。第二个脚本通过 Electron 发送鼠标事件，结果写入 `workspace/diagnostics-benchmark/results.json`。为每轮首次资源加载设置不同的 `SINKING_STAR_PERF_COLD` 值可使用独立的派生缓存；操作系统文件缓存保持原状。

### 试玩副本空间盘点

| 受管试玩副本目录 | 文件总大小 | NTFS 文件分配 |
|---|---:|---:|
| 整份副本 | 14.31 GB | 14.35 GB（13.37 GiB） |

原安装在 D 盘，试玩副本在 E 盘，二者均为 NTFS。逐文件只读检查发现，`data-pc` 的 9,666 个原版模型和贴图与试玩副本同路径文件 SHA-256 一致，共 3,518,491,350 字节。副本另外有 1 个该目录下的生成资源；其部署登记共 183 个辅助文件，分布在资源目录中。匹配数据仅用于评估候选范围。跨盘不能使用硬链接；目录链接也不会让目标变成只读。[Microsoft 的 NTFS 链接说明](https://learn.microsoft.com/en-us/windows/win32/fileio/hard-links-and-junctions)

| 试玩流程 | 实际写入位置 |
|---|---|
| 准备和版本更新 | 工作区暂存目录，校验后替换受管副本 |
| 部署关卡 | 副本内 `data/levels.package`，以及 `data-pc` 贴图别名和 `data-common` 涂装、光照等资源 |
| 启动和运行 | 副本的独立启动程序和日志，受管会话的设置和存档目录 |

目前未验证游戏能从独立只读目录读取模型和贴图，同时在副本内覆盖同路径的生成资源。因此继续使用完整副本，空间占用未减少。当前原安装预计复制 14.54 GB 文件（忽略日志），准备空间校验合计要求约 15.21 GB 的新增可用空间，包括关卡包备份和 256 MiB 余量。有旧副本时两份会在校验替换期间短暂并存。这里只读盘点了现有文件；实际复制峰值和吞吐未重新测量。

PowerShell 7 中运行 `./scripts/playtest-space.ps1 -GamePath '<Steam 游戏目录>' -TestCopy '<工作区中的 playtest-game>' -VerifyAssets` 可复查。脚本跳过链接，分别统计逻辑长度和 Windows 报告的文件分配量，不计目录元数据；加 `-VerifyAssets` 才读完整文件校验哈希。

| 项目 | 实测 |
|---|---:|
| 后台首次读取原包、反射并索引 204,988 条记录 | 1,458 ms |
| 界面首次获得索引并打开工作区 | 915 ms |

选择取 4 次预热加 30 次测量；反馈测到视口 probe 反映所选 ID，25ms 轮询间隔使数值偏保守。镜头拖动取 45 帧并去掉前 5 帧，物件移动取 35 帧并去掉前 5 帧。使用真实 Electron 输入事件与原生模型，不是仅修改 React 状态。渲染 CPU 为 renderer.render 调用耗时，未测 GPU 栅栏。

大型天空分区最初选择 P95 为 396.4ms；发现属性引用下拉一次生成数千个选项。改为展开检索、虚拟列表和延迟配置图卡后，按相同场景复测为 26.5ms。拖动期间分区请求数不增加，未编译关卡；松手只提交一步，Esc、失焦和视口外释放不补交。

数据后台较重的三层分区（含相邻区）首次处理：地面 467 记录／3,350 地形格，70ms；地下 507／3,987，44ms；天空 3,446／6,893，151ms。缓存再次请求为 0.13–0.31ms，只代表后台缓存查询，未计 IPC、模型和绘制。原版多高度小关 green_metamirror 首次数据预览 121ms。

# v0.7.9 性能记录

本轮为可重复的自动基准，不能替代用户对完整编辑器手感或游戏机制的验收。没有同条件的旧版基线，因此不宣称相对旧版的提升倍数。

## 条件与范围

Windows x64，Intel Core i9-14900HX，Electron 45，1366×768 隐藏的独立 Chromium 测试窗口；与用户配置、存档及当前窗口隔离。100／1,000／5,000 个 Rock 使用简化几何代理；另测原版 `green_metamirror` 的 2,665 条实体及实际模型。代理场景不能代表 5,000 个复杂原生模型的开销。

每个场景取 30 次选择、120 次本地拖动帧反馈、30 次半透明代理预览。选择／预览反馈测到下一次动画帧；拖动反馈逐帧测量，渲染 CPU 记录 `renderer.render` 的时间，未做 GPU 栅栏测量。首次阶段包含该场景的资源准备，后续统计为预热结果；操作系统磁盘缓存未清空，各场景共用进程资源缓存。内存是渲染进程 JS 堆的阶段净变化，受垃圾回收影响，不是整个编辑器的总占用。

## 实测（毫秒；内存 MB）

| 场景 | 首次准备 | 选择 P95 | 拖动反馈 P95 | 拖动渲染 CPU P95 | 代理预览 P95 | JS 堆净变化 |
|---|---:|---:|---:|---:|---:|---:|
| 100（简化物件） | 155.2 | 19.2 | 18.1 | 0.4 | 32.6 | 5.8 |
| 1000（简化物件） | 35.5 | 20.1 | 18.0 | 1.4 | 33.7 | 6.1 |
| 5000（简化物件） | 113.8 | 24.7 | 18.3 | 5.3 | 32.5 | 39.4 |

本轮这些预热场景达到选择／代理预览 100ms、拖动反馈 33ms 的目标。该结论只覆盖上述脚本路径；完整应用的新原生物件放置、超大组合与低配置电脑仍需用户测试。原版关首次准备 303.9ms，首次资源加载仍可能出现等待。

## 原生预览处理

独立后台线程对同一原版关执行 30 次已提交位置修改：首次请求 514.3ms，预热往返 P95 72.0ms（包括请求、原生处理和差量传输）。首次全量 JSON 约 2,899,364 字符，常规位置修改差量 P95 1,879 字符。复杂操作可完整重建；差量传输不等于只运行几行原生解析。

此独立 Node 测试进程及线程的 RSS 从 64.4MB 到 619.1MB，包含游戏包、程序反射、缓存和工作线程；预览缓存会保留多份修订，内存仍有优化空间。该数字不是整个 Electron 编辑器的实测总占用。

## 自动界面与事务检查

实际 StudioApp 独立测试中，选择、创建分组、撤销分组均没有新增预览请求；一次属性提交只有一次原生预览请求。检查分组保存、锁定删除拦截、命令同义词与键盘焦点。在 1366×768、1920×1080 及 Electron 150% 页面缩放下检查画布和命令窗口并审阅截图；页面缩放不等同于完整的 Windows 多显示器 DPI 验收。

视口脚本确认 300ms／80ms 连续微移、释放后一次提交，以及 Esc／失焦后恢复原位且计时器不补交。原生数据回归与上述界面检查不启动游戏，不证明实际通关或特殊机制正确。

## 复现

安装开发依赖并完成 `npm run build`。设置 `SINKING_STAR_GAME` 指向自己的 Steam 游戏目录，然后分别运行：

```powershell
node scripts/benchmark.mjs
npx tsx scripts/benchmark-native.ts
node scripts/ui-check.mjs
```

结果写在本机 `workspace/benchmark-v079` 和 `workspace/ui-check-v079`，不纳入公开源码；不要同时运行多组基准，以免互相争用。基准不部署测试副本，不连接或切换游戏战役。
